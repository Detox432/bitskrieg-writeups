# Quizploit - Binary Exploitation


## Approach
I was given 2 files, one called vuln.c and a binary file called vuln. My first instinct was to check the contents of both files. From nano vuln.c, The comments suggested this code was  only supposed to only be a template over which questions would be asked. Also compiling vuln.c with gcc gave an error ![gcc vuln.c](image-1.png). Next step was to analyze the vuln binary file. Using file suggested that this file was an executable ![file vuln](image-2.png)
using chmod +x vuln to change the permission of vuln to become executable (since it wasnt before), i was able to run it. Running vuln asked us to "Enter payload:" similar to what  the code in vuln.c suggested. Entering simple strings like "hello" or "123" or "a" all returned nothing from the program. Upon entering a big enough string, the program would crash due to a segmentation fault. This was evident from the fact payload was only excepting 0x15 bytes. I also used xxd vuln | less and decompiled it using ghidra to see if i could find any clue. From the vuln.c it was obvious that i had to somehow find a way to run the function win() which would cat flag.txt and give us the flag. The input field was also interesting since it was only accepting 0x15 length of input (proved by segmentation fault when i entered something big) but it was still displaying 0x90 length of output. After all this analysis I connected to the instance and started answering the questions

## Solution
First 3 Questions were very easy, all answered by file vuln as it was 64 bit, dynamic and not stripped, the 4th question was also seen in the vuln.c file where it was defined like this ![vuln.c picture](image-4.png) suggested 0x15 as the size of the buffer. The fifth question leads on directly into this cuz in that image it shows that at the end 0x90 byets are being read into the buffer. Question 6 was also very obvious since size of buffer being read was more than the input, hence leading to a bufer overflow vulneribility ![buffer overflow](image-5.png).
For Question 7, it was obvious that fgets was causing the buffer overflow vulneribility since it was reading 0x90 bytes. Question 8 the name of the function was win() which was needed to cat flag.txt and get the flag. Question 9 was also self explanatory as the attack was buffer overflow. Question 10 the number of bytes of overlow which was possible was simply 0x90 bytes - 0x15 bytes, since this is hexadecimal, doing the substraction results in a buffer  size of 0x7B or 123. Quesiton 11 pointed out my oversight as I had not used checksec during my initial approach, upon using checksec ![checksec](image-6.png), we saw only NX protection was enabled so the answer was NX. For Question 12 since PIE was disabled and no stack canary was present, to exploit the buffer overflow we couldve used a method called ROP or a simpler version (ret2win) where since we had the unused function win() that would cat flag.txt we could overwrite the return address using buffer overflow to have the return address of win() so that it could run our desired output instead of returning nothing or wtv it was originally doing ![ROP](image-7.png). For the last question, question 13, it asked us to find the adress of the win function, since i had already decompiled and analysed the code in ghidra, the address was easily found ![ghidra of win function](image-8.png) to be 0x401176.
